# Changelog

All notable changes to SRP VPN Connect are recorded here. Every commit adds its entry under **Unreleased**; a TestFlight or App Store build moves those entries under its version and build number.

## 1.2.0 (41) - 2026-11-10

### Added
- The DNS resolver option for WaterWall profiles on iPhone and Android (WaterWall Configuration, DNS RESOLVER): Resolver Off, the default, leaves names to the server as before; Native, Direct and Through the VPN have WaterWall look names up before routing, with the DNS of the network the phone is on, with DNS servers of one's own outside the VPN, or with those servers through the VPN, so that GeoIP routing sees the real addresses. Addresses picks IPv4 or IPv6 first or only; DNS Servers takes 1 to 32 IPv4 or IPv6 addresses, each with an optional port. Through the VPN needs a chain that carries UDP as well as TCP, and the app says so before it saves.
- Aether profiles have Auto Reconnect, Retry Times and On Sleep on iPhone. The app counts as connected once a test connection through the tunnel went through, sends one every 20 seconds and one at once after a change of network, and counts two failures in a row, or the end of the engine's session, as a lost session (a failed test after which 64 KB or more came back through the tunnel does not count: Tor gives a new stream up after 10 seconds on a busy circuit): Auto Reconnect then sets up a new one, 2 seconds after each failed attempt, Retry Times limits the attempts (before the first connection it adds attempts), and without Auto Reconnect the VPN ends with the reason. On Sleep Off and Pause close the session while the device sleeps; at wake Pause connects again, and Off only with Auto Reconnect. With the WireGuard transport the app's WireGuard does this with its own handshake check. There is no Switch to Wi-Fi option: Aether follows the phone's network.
- Aether's Private mode on iPhone has Import Config (.conf), Manual Configuration, Server and Port: an imported file fills Server and Port from its Endpoint, and changed, they replace it. An AmneziaWG file is refused (the server speaks plain WireGuard). The messages tell a server that never answered the WireGuard handshake from one whose Aether proxy refused the connection (is the aether container running?).
- The Aether log in Release builds of the iPhone app: Normal has the milestones and the reason a connection ended, Expert a line for each test connection that went through (the session's age and the bytes each way), Debug the engine's own lines and one for each connection. No level writes a key or the WARP+ license.
- Aether in the Android app: the engine of our Aether fork (tag v2.4.0-srp.2) built for arm64 by cargo-ndk into libaether.so, with its JNI layer and hev-socks5-tunnel in libsrpaether.so, and the iPhone app's connection logic, options and messages (`AetherClient.kt`): Public mode over MASQUE (HTTP/3, HTTP/2, both) with the endpoint scan, the WARP+ license (kept in the secret store), TLS Fragmentation and Tor (WARP via Tor, Tor Only), or over WARP's WireGuard through the app's WireGuard; Private mode over a userspace WireGuard (wireguard-go's netstack, beside the engines in libwg-go.so) to one's own server's Aether proxy; the test connection every 20 seconds and after a change of network, Auto Reconnect, Retry Times and On Sleep with the screen. The editor has the iPhone's rows, footers and checks; the home screen shows Cloudflare WARP for Public mode, which connects without a server. Tor's state directory is the app's own, so Arti's check of its parents' permissions is turned off (Android's /data/user/0 is writable by the system group).
- Aether documentation for both apps (`tutorial/aether/`): Public mode, which needs no server, and Private mode with a server on Ubuntu 24.04 (WireGuard for the phones and our Aether engine in Docker, built from tag v2.4.0-srp.2, with its SOCKS5 port only on the tunnel's address, the WARP edge's certificate checked, Docker started after WireGuard, and scripts that add and remove a phone), every step run on the test server and then used by both phones; setting up both apps with screenshots, what each setting and each line of a phone's file does (Configuration Reference), what each message means (Troubleshooting) and every case on both phones (Test results, 43 of 43 on each).

### Changed
- The app's WaterWall is upstream's official v1.5.42 (with our client-only changes), the version our test server now runs. 1.5.4 and later refuse `domain-strategy` and `resolve-domains` on a node, so both apps write `dns-behaviour` instead, and profiles saved earlier keep their choice: Do Not Resolve becomes the default, which does not resolve, and the other strategies resolve on the phone with that strategy. 1.5.42 also stops raising the server's socket buffers to 128 MiB at start and keeps its TCP memory to 15 % of RAM; neither applies to the apps, which turn this tuning off.
- The WireGuard and AmneziaWG documentation name TestFlight build 40, the first with their code.
- The documentation: every guide's iPhone screenshot of the Protocol screen no longer shows Psiphon, Future protocols no longer lists it (every protocol in the app now has its guide), and the home page says the app has the same protocols on iPhone, iPad and Android.
- The Android app's version code is 8, for the release APK that adds Aether; the version name stays 1.2.0.
- The Android app's version code is 9, for the release APK with WaterWall 1.5.42 and the DNS resolver option; the version name stays 1.2.0.

### Removed
- Psiphon VPN is no longer in the iPhone app: its profile type, editor, Server Entries screen and tunnel engine are gone, and the shared Go runtime (libsrpwg-go.a) carries only WireGuard and AmneziaWG. Saved Psiphon profiles leave the list when it loads. The README, the third-party notices and the documentation no longer name it.

### Fixed
- Aether's Private mode: a name looked up as the second of a session got the tunnel's own address (198.18.0.1) as its stand-in address, and connections to it were refused. The stand-in addresses now come from 198.19.0.0/16.
- The WARP+ license no longer appears in the app's log or the tunnel's log when an Aether profile connects.
- The Aether profile editor on iPhone shows the footer under Server, which explains Public and Private mode; it was hidden.
- Aether on iPhone builds the engine from our fork's tag v2.4.0-srp.2, which writes the destination of each SOCKS5 request only at debug level, so a Private mode server no longer keeps a list of every place its phones connect to.
- Aether on iPhone over MASQUE (HTTP/3, HTTP/2 and both): uploads no longer stall the connection. The engine dropped the packets its TCP stack sent whenever the queue to the carrier was full, and that TCP, which has no congestion control, kept resending into the same full queue until every connection stalled (four 16 MB uploads over HTTP/3 never finished, or crawled at 5 Mbit/s; over HTTP/2 10 Mbit/s). The app now builds the engine from our fork (github.com/bigmoveus/Aether, tag v2.4.0-srp.1: upstream v2.4.0 with the app's earlier patches as commits and this fix), where those packets wait until the queue has room: on an iPhone 12 uploads reach 104 Mbit/s over HTTP/3 and 167 over HTTP/2.

- SSH VPN logins through the server's keyboard-interactive (PAM) method when it offers no password method; the app answers the prompt with the profile's password.

- The SSH log in Release builds of the iPhone app, with the server's host key, the login, the reason a session ended and, at Expert, the transfer counters; no level writes the password.

The home page, the navigation and the future-protocols page list SSH VPN.
- OpenVPN messages that say what to fix: a name that does not resolve, a TCP port where nothing listens, a UDP server that does not answer (10 seconds instead of 45), a server that stops answering after the TLS handshake (it refused the client certificate), a refused login, a server certificate the profile's CA did not sign, no common data-channel cipher, a static-key or passphrase-protected profile, and for stunnel an untrusted certificate, a certificate the imported CA did not sign, a refused or unreachable port and a closed connection.

### Changed
- The SSL VPN documentation names TestFlight build 38, the first with the Path field.
- The SSTP documentation says that a password may hold any character, and that RouterOS's local secrets and SoftEther take one with characters outside ASCII at the app's second attempt.
- Both apps' WaterWall follows upstream main at `ecdbb3947` instead of `ccb40eafd`, keeping the apps' own client changes. Upstream now negotiates TCP timestamps in its lwIP on every platform (radkesvat/WaterWall#352, merged 2026-11-07), and it renamed the KCP nodes `TcpOverUdpClient` and `TcpOverUdpServer` to `KcpClient` and `KcpServer` with no fallback, so the apps' chain builders now write `KcpClient` (Android's parity fixture regenerated from the iOS builder); the KCP wire format is unchanged and the apps still connect to official v1.5.3 servers. Two local changes upstream lacks at this commit: `ww` passes `-Wno-shorten-64-to-32` to the tunnels on Apple, as it already does for other Clang builds (upstream's iOS and macOS builds stop on size_t narrowing under `-Werror`), and PacketsToConnection's UDP startup queue uses the renamed `bufferqueueGetEntryCount`. Tested: iOS 181 and Android 16 unit tests; Raw IPv4 + KCP on an iPhone 12, 4 alternating pairs against the official v1.5.3 server (1 of 4 stalled) and upstream main's GitHub Actions build of the same commit (0 of 4), and on a Samsung Galaxy A55 (none stalled with either). Other chains were not run again.
- OpenVPN: a server that pushes compression (lz4-v2, comp-lzo) is refused with a message instead of failing silently; compression inside a VPN can leak data (VORACLE).
- OpenVPN: the Server and Port fields take effect. Changed, they replace the profile's remote line; as the import fills them, a profile's several remote lines are tried in order.
- The Android app's version code is 4, for the release APK that adds SoftEther VPN, SSL VPN, SSH VPN and OpenVPN; the version name stays 1.2.0.

### Fixed
- SSH VPN on iPhone: a download no longer ends the VPN. The packet pump kept every received packet in memory until the session ended, and iOS stopped the tunnel at its 50 MB limit within seconds.
- SSH VPN: with UDP Relay off, the first UDP packet of an app (a QUIC connection, for example) no longer crashes the tunnel. The engine freed that packet twice.
- SSH VPN: a connection no longer gets another connection's data. libssh2 keeps one channel open in progress per session, so two connections that opened at the same time could swap their channels. Each channel now opens on its own (a small addition to the vendored libssh2: `libssh2_channel_direct_tcpip_start` and `libssh2_channel_open_result`), so one slow destination, or a slow name lookup on the server, no longer holds up the others.
- SSH VPN: the session no longer stalls under load. When the socket took a keepalive or an end of stream only in part, libssh2 refused every other send until the same call came again, which for those never happened. The bridge now queues what the socket cannot take yet, so libssh2's sends always go whole.
- SSH VPN: many connections at once no longer stall. The packet channel between the tunnel and the packet engine held 512 KB, and when it was full the system refused packets instead of waiting, so the engine's TCP backed off; it now holds 4 MB. 16 downloads at once ran without errors in our tests.
- SSH VPN: the last bytes the server sends together with its end of stream reach the app.
- SSH VPN: the placeholder addresses the tunnel gives names no longer include its own address and its DNS server's; each session takes them from another range, and a reconnect applies the settings again, so the system forgets the old ones.
- SSH VPN profiles reconnect. Auto Reconnect and Retry Times now open a new SSH session when the connection breaks, the server ends the session, or keepalives go unanswered for 50 seconds; without Auto Reconnect the VPN ends with the reason instead of staying up without a tunnel. Switch to Wi-Fi opens a new session over Wi-Fi when it appears, and On Sleep works as for SSL VPN.
- An SSH profile without a port connects to port 22; it used 443.
- SSH Host Key: the app asks for the server's keys in OpenSSH's order, so a server with an ED25519 key shows that one (libssh2 preferred ECDSA, and the ED25519 fingerprint that `ssh` shows never matched). The field also takes the whole line `ssh-keygen -lf` prints, and a mismatch names the key the server presented.
- SSH passwords that hold ":" or characters whose base64 has a "/" (such as "?" or letters outside ASCII) reach the server as typed.
- The SSH bridge keeps its own copy of the profile's strings; it read them after their buffers had gone.
- SSH VPN on Android: a connection the server resets is named as reset ("The connection was reset", or "the connection was reset; reconnecting" with Auto Reconnect) instead of as closed by the server. Linux reports the reset once and an end of stream on every read after it, and the shared bridge looked at the end of stream first; it now looks at the socket's error first, on both systems.
- SSTP, SoftEther VPN, SSL VPN and OpenVPN passwords that hold ":" or spaces at their ends, or characters whose base64 has a "/" (such as "?" or letters outside ASCII), reach the server as typed, as SSH passwords already did. The iPhone app hands each profile's login to its tunnel inside an address; such passwords broke that address, so the VPN did not start, or lost their spaces in the tunnel. The address now carries the login in base64's URL-safe alphabet for every protocol, and the tunnel still reads the ones older versions saved.
- SSTP on iPhone: a username, password or EAP anonymous identity with characters outside ASCII reached the login as whatever had been left in freed memory, so every server refused such a password. lwIP keeps only the pointers it is given, and the buffer `UTF8String` gives for such a string goes with the autorelease pool; the app now keeps the bytes for the session.
- SSTP: a password with characters outside ASCII is hashed for MS-CHAP as UTF-16, as Windows and FreeRADIUS do, instead of one byte per character (MS-CHAPv2, EAP-MSCHAPv2 inside PEAP, TTLS and TEAP, and the SSTP crypto binding; `iOS/LwIP/lwip/include/netif/ppp/srp_utf16le.h`). RouterOS's local secrets and SoftEther hash such a password byte by byte, so when a server refuses it the app tries once more that way, on both phones. Tested on an iPhone 12 and a Samsung Galaxy A55 with a password of Persian letters and a Latin-1 letter: Windows Server 2022 (MS-CHAPv2 and PEAP) and FreeRADIUS through MikroTik at the first attempt, a MikroTik local secret and SoftEther 4.44 at the second. On Android a character past U+FFFF, which JNI passes as two surrogates, hashes as the same UTF-16 pair as on iPhone.
- The app's log line about a built tunnel URI masks the username and password before it shortens the line to 60 characters; a long username and password pushed the "@" past the cut, and their base64 stayed in the log.
- OpenVPN on iPhone: a download no longer ends the VPN. The core's callbacks kept every packet in memory until the session ended, and iOS stopped the tunnel at its 50 MB limit within seconds.
- OpenVPN with stunnel: a UDP profile goes through stunnel as TCP. It went straight to the server over UDP and skipped stunnel, as the core's protocol override only filters remote lines.
- OpenVPN stunnel CA Certificate: the imported CA is checked. With a CA imported the app accepted any certificate (its check always succeeded, and the PEM was handed over where DER was expected).

Both now say 1.5.2, and the last six files of that release (PingClient and PingServer, which the app does not build) are in place. The WaterWall compiled into the app does not change.
- WaterWall could stop all traffic for about half a minute until the health check closed the tunnel. A lock in its event loop could miss a wakeup on the phone's ARM processor, and the worker thread then slept until the tunnel was stopped.
- After each WaterWall KCP connection the app kept the line for up to 30 seconds, retransmitting its close frame and waiting for an acknowledgement servers never send, and each retransmission opened a useless line on the server. It now waits only until its data is acknowledged, sends the close frame once and releases the line, and sends nothing more once it reads the server's close frame. Uploads of many small requests went about twice as fast in our tests.
- A new WaterWall KCP connection could get a UDP port a recent connection had used and reach what the server still kept for that port. It then received nothing, and a TLS connection through it failed after hanging for a minute. A UDP port now stays out of use for 60 seconds after it is released.

## 1.2.0 (30) - 2026-11-02

### Added
- A documentation site in `tutorial/`: static HTML guides for WaterWall (installation, getting started, configuration, the app's screens, troubleshooting and FAQ) and one page for each of the 163 scenarios tested on the phone against WaterWall 1.5.2, with its server file, app settings, procedure and result. `tutorial/tools/waterwall_scenarios.py` turns a device test run into sanitized evidence files and renders the scenario pages from them; it refuses to write a file that still holds a public address or a local path. SSTP follows later.
- SSTP profiles with Proxy set to Auto (PAC) take a username and password for the proxy the PAC script picks; before, a PAC proxy that asks for a password could not be used.
- The WaterWall Advanced Node Settings editors (Packet, Application and the other layers) work as a JSON editor. A line under the text says whether the JSON is valid or names the line and column of the first error, as the save alert now does too; a new line keeps the indentation, one level deeper after `{` or `[`; and Format pretty-prints valid JSON.

### Fixed
- SSTP crashed the VPN extension as soon as a connection started, because WaterWall's lwIP network stack had replaced the one SSTP uses. WaterWall's copy now has its own symbol names, so each protocol keeps its own stack.
- SSTP could crash the VPN extension under heavy traffic: every batch of packets read from the device replaced the callback that was writing received packets back. It is now set once, and a reconnect no longer starts another read loop.
- An SSTP upload faster than the path to the server made the VPN extension exceed its memory limit within seconds. The tunnel now stops reading from the device while 1 MB waits for PPP framing or for the network, with or without TLS Fragmentation.
- Under upload, every finished SSTP send processed the PPP buffers again on the network queue while the tunnel was filling them, which could corrupt frames.
- With TLS Fragmentation, SSTP kept a copy of every encrypted chunk it sent, so an upload ran the VPN extension out of memory within seconds.
- Heavy SSTP traffic, such as eight downloads at once or any download with TLS Fragmentation, could run the VPN extension out of memory. The objects each packet left for release piled up while the packet queues never went idle, and with TLS Fragmentation every read took everything the network had buffered. Each batch of packets now releases its objects, and TLS Fragmentation reads at most 64 KB at a time.
- SSTP could crash the VPN extension when a connection closed with sends still in flight, as when the device slept with On Sleep set to Pause or Off, or on a reconnect.
- After the server ended an SSTP session, Auto Reconnect gave up instead of reconnecting when Retry Times was unlimited, because the drop was taken for a connection that never came up. Late events from a replaced connection no longer reach the new one.
- When an SSTP connection ended for good after it was up (Auto Reconnect off, Retry Times used up, or On Sleep set to Off without Auto Reconnect after the device woke), the VPN stayed connected without a working tunnel; it now disconnects with a message.
- SSTP sent a Custom SNI that was switched off when the profile still held its hostname.
- With Custom SNI on, the certificate check before an SSTP connection ignored it and reported an untrusted certificate when the Host field is an IP address; it now checks the certificate against the Custom SNI, as the connection does.
- When an SSTP server ended PPP before the first link came up, for example because it accepts none of the profile's authentication methods, the error read "Connection lost (auto reconnect is off)."; it now says the server closed the connection during PPP negotiation.
- An SSTP profile that uses only PEAP, EAP-TTLS or TEAP could not be saved.
- SSTP ran the TLS Fragmentation mode that was not chosen: Manual ignored the chunk sizes and used the automatic ones, and Auto used fixed 32- and 256-byte chunks. Each mode now runs as chosen.
- The SSTP profile editor accepted Manual TLS Fragmentation chunks above 4096 and 16384 bytes, which failed only when connecting; it now names the limit on save.
- An SSTP proxy that cannot be reached was reported as an unsupported proxy protocol after about 20 seconds; the error now names the proxy address and the reason, at once when the connection is refused.
- A wrong password on an SSTP server that ends the call together with its refusal, as MikroTik does with RADIUS, was reported as a failed negotiation of the authentication methods; it is now reported as a rejected username or password. A server that ends PPP without a refusal gets a message naming the phase it ended: negotiation, authentication or the tunnel address.
- When an SSTP server ended the call but kept its TCP connection open, as SoftEther does when it accepts none of the profile's authentication methods, the connection waited 30 seconds and then said the server did not respond; it now ends at once with the reason.
- SSTP answered an EAP-MD5 challenge with the password whichever EAP methods the profile allowed. FreeRADIUS offers EAP-MD5 first, so PEAP, EAP-MSCHAPv2 and certificate profiles behind it logged in with EAP-MD5 instead and passed no traffic (EAP-MD5 gives no keys for the crypto binding), and any server could obtain a hash of the password to guess at. The profile's own method is now asked for, and unknown methods are refused the same way.
- With Identity Privacy on, a server that refuses the anonymous outer identity, as Windows RRAS does with local accounts, was reported as a wrong username or password only; the message now names Identity Privacy too. A refused client certificate is reported as such instead of as a wrong password.
- With EAP TLS 1.3 on (the default), PEAP and the other TLS-based EAP methods failed against Windows Server NPS, which has no TLS 1.3 for EAP and drops the offer. When a server ends EAP during the TLS handshake of a TLS 1.3 offer, SSTP now connects again once, offering TLS 1.2.
- In the WaterWall Advanced Node Settings editors and the Psiphon Server Entries editor, opening the keyboard moved the whole screen up, so the back and save buttons sat under the status bar. The screen now stays in place; the text still ends above the keyboard.
- A WaterWall Reality profile with the SNI left empty sent the server's name instead of the www.cloudflare.com cover the profile editor describes. An empty SNI means www.cloudflare.com for Reality again, as before the tunnel started connecting to the resolved server address.
- WaterWall TLS Fragmentation set to Auto used the Manual chunk sizes stored in the profile. Auto now always cuts at 32 and then every 256 bytes; only Manual uses the profile's sizes.
- With BGP4 Framing and an HTTP or WebSocket layer both on, WaterWall left the HTTP layer out of the chain. HTTP now sits inside the BGP4 framing, in the order the configuration screen lists them.
- A WaterWall SNI hidden because the outer layer has no TLS (None, AEAD or BGP4) was still sent as the HTTP Host; it is now ignored and the Host is the Server field.
- Ticking countries for WaterWall GeoIP routing while the GeoIP Routing switch was off turned routing on without installing the country database, so the connection failed; ticking a country now installs it as the switch does.
- Tapping the protocol a profile already has in the Protocol list reset the profile to that protocol's defaults, and tapping the current WaterWall Application cleared its UUID or password. Both now leave the profile as it is.
- An empty Port in WaterWall's WireGuard mode connected to 443 although the field showed 51820; it now means 51820.
- The WaterWall KCP settings check measured kcp-initial-cwnd against a send window of 8192, while the chain uses 128 unless kcp-send-window is set.
- The WaterWall profile editor accepted a Manual TLS Fragmentation First Chunk of 16384 bytes or more, which leaves the ClientHello whole; it now names the limit on save.
- A profile kept its WireGuard keys and settings when its protocol changed, so a WaterWall profile in WireGuard mode could connect with keys entered for the WireGuard, AmneziaWG or Aether protocol, and the other way round. A profile moved to another protocol now starts without them.
- WireGuard private keys, preshared keys and imported configs were saved in the app's settings file. They are now kept in the Keychain and the profile keeps only a reference; saved profiles move their keys there when the app first loads them.
- A saved WireGuard profile that had both an imported config and manual keys lost the import when the app loaded it. Only a config generated from the manual fields is now dropped on load.
- Deleting a profile left its passwords and WireGuard keys in the Keychain; they are now removed with the profile.

### Changed
- New profiles start as WaterWall VPN with its default configuration on port 443 instead of SSTP; existing profiles keep their protocol.
- The SSTP tunnel log records the extension's memory when the link comes up and, near the memory limit, how much data waits for PPP framing and for the network.
- SSTP accepted any certificate from an EAP server on another host than the SSTP server, as when RRAS relays PEAP, EAP-TTLS, TEAP or EAP-TLS to a RADIUS server. That certificate must now chain to a root the device trusts, as the outer connection's does, unless Allow Insecure is on; a RADIUS server with a private CA needs that CA installed and trusted on the device. A refused certificate is named in the error.
- WaterWall's Auto Switch option is shown only in Chain mode, because WireGuard and Direct have no other profiles to switch to. Its note now says that a network change returns to the chosen profile when Switch to Wi-Fi When Available moves the connection.

### Development
- The WaterWall runtime build fails when one of WaterWall's lwIP symbols keeps a name the other protocols' lwIP uses (`WaterWall/tests/lwip_prefix_contract.py`); `WaterWall/generate_lwip_prefix.py` regenerates `srp_lwip_prefix.h` after an lwIP upgrade.
- Live device tests for a profile of any protocol: `testProfileLiveConnectionAndThroughputWhenConfigured` runs downloads, uploads or both, or expects a refusal, and `testProfileLiveLifecycleWhenConfigured` checks the sleep modes, a session the server ends and the retry limit. The profile comes as JSON in `SRP_LIVE_PROFILE_JSON` and its password in `SRP_LIVE_PASSWORD`; `SRP_ACCEPT_UNTRUSTED` answers the untrusted-certificate prompt.
- A live connection that does not come up no longer fails the test on its own timeout, so a test that expects a refusal can pass.
- The live profile tests can log in with a client certificate: `SRP_LIVE_CERT_P12_BASE64` carries the PKCS#12 and `SRP_LIVE_CERT_PASSPHRASE` its passphrase. The test imports it as the profile editor does and removes it afterwards.
- The unit tests link in Release builds again. Tests added since 31 October referred to app classes directly, which the Release app does not export; they now reach them through `NSClassFromString`, as the other tests do.
- `testDocumentationScreenshotsWhenRequested` renders the WaterWall screens with example values for the documentation when `TEST_RUNNER_SRP_DOCS_SCREENSHOTS=1` is set.
- The device matrix's server side no longer requires an HTTP Host, because the generated client and the app may send different names by design.
- The device matrix builds its BGP4 framing cases with the `bgp4` configuration switch. It put the flag in node-options, which the app refuses, so none of those combinations ever ran.
- The device matrix's GeoIP cases check the routing: the reference server's log shows whether each download came straight from the phone or through WaterWall. Before, they only measured traffic.
- The live tests' sustained UDP check waits up to 60 seconds past its duration instead of 20, and its log line counts the datagrams it sent again. Each lost datagram costs a 5-second retry, so paths that lose a few in 90 seconds ran out of time although UDP worked. The TCP ping test logs the state its default-route check ends in.
- The runtime recovery test waits for WaterWall to stop before it waits for the restart. It checked for the restart while the old runtime still reported itself up, so its second round of downloads and UDP began before the restart.

## 1.2.0 (29) - 2026-10-31

### Added
- Auto Switch for WaterWall profiles, on by default under Options: when the connection fails, Auto Reconnect tries the next WaterWall profile of the same server, and when the network loses too many packets (15% of the packets sent within 30 seconds, or two connections dropped within two minutes) the connection moves to a profile with the other carrier (TCP or UDP) that has not lost packets on that network yet. A network change returns to the selected profile.
- WaterWall measures its TCP connections to the server (packets sent and retransmitted, data received, round-trip time, retransmission timeout and connections the network dropped) and writes a summary to the log every minute while traffic flows.
- The measurement also covers the UDP carriers: KCP segments sent again, QUIC packets declared lost, and KCP or QUIC sessions that stopped hearing from the server. Auto Switch therefore moves a lossy KCP or QUIC connection to a TCP profile as well.

### Fixed
- TCP ping skipped WaterWall profiles that carry QUIC over a TCP stream; they are pinged like the other TCP transports now.

### Changed
- WaterWall VPN comes first in the protocol list of the profile editor.

### Development
- The `--lifecycle` device run checks that Auto Switch connects through another profile of the same server when the selected one cannot reach it, and that the outer TCP connections are measured.
