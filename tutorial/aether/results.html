Test Results

Every Aether case we ran on 9 November 2026, with its result on an iPhone and on an Android phone: 43 of 43 cases passed on the iPhone and 43 of 43 on Android.

How these tests ran

The phones were an iPhone 12 with iOS 27.2 and a Samsung Galaxy A55 with Android 17, with the code of commit 968a86a7 on both phones: on the iPhone a Release build, the kind TestFlight ships, and for the ae-life-… rows a Debug build, which the lifecycle test needs; on Android a debug APK, for most rows of the build just before 968a86a7, which differs only in how a test connection that fails while traffic still comes back counts (ae-tor-only, ae-both-upload, the ae-life-… and the ae-guide-… rows ran on 968a86a7 itself). Public mode connected to Cloudflare WARP from our office line. The server of Private mode was our test server (Ubuntu 24.04 with Linux 6.8, 12 vCPUs): WireGuard's wg0 on UDP port 51820 with the address 10.66.66.1/24 and a peer without a preshared key, and the aether container of our fork's image v2.4.0-srp.1, whose engine is that of v2.4.0-srp.2 except for the log level of its SOCKS5 request lines; for the ae-guide-… rows, the same server set up again as Aether server shows, with v2.4.0-srp.2.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server that logged where each request came from. Every case that moved traffic checked that the requests came from a Cloudflare address (AS13335), so they left through WARP; with Tor Only, from outside Cloudflare.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both; the row shows how long that took.
  • The server's view. In the Private cases that moved traffic, the server's WireGuard log showed the phone's handshake.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row.
  • Log levels. The cases named ae-log-… and ae-private-log-… moved 40 seconds of downloads (10 seconds at Debug), read the connection log back and checked its lines; no level may show a key or the WARP+ license. The iPhone ran them on a Release build, the kind TestFlight ships. At Debug the check looks for the engine's and the packet bridge's lines, which only that level writes.
  • Lifecycle. The cases named ae-life-… checked On Sleep; a session that ends; a change of network; the server's WireGuard port dropping every packet for 40 seconds, for 70 seconds without Auto Reconnect and for 160 seconds with Retry Times 2; and the server's aether container stopped. On Android the screen was really turned off, Wi-Fi was really switched off and on again, and the session was ended with the debug build's test command.
  • The guide's server. The cases named ae-guide-… ran last: the test setup was moved aside, the server was set up again with the steps of Aether server as the page shows them, and the phones used the page's own files for iphone1 and android1 and the removed phone2.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line, to WARP's nearest edge. They show that traffic moved, and are not a benchmark. The Android phone was on office Wi-Fi with a slower uplink than the iPhone's.

Not tested in this round

  • A valid WARP+ license. The case used a key WARP does not know; binding a real one was not tried.
  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel test the session as after a change of network, without a real one.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel, and a server with an IPv6 address.
  • A reboot of the server. The guide's drop-in that starts Docker after WireGuard was tested by stopping both and starting Docker, not by a reboot.
  • Importing a file through the app's screens. The cases gave the app the file's text as an import does.
