How these tests ran

The phones were {iphone} and {android}, with {app}. The server was {server}, set up as OpenSSH server describes.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server on the internet. That server logged where each request came from, and every case that moves traffic checked that it came from the SSH server's address, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both, and ssh-many-connections ran 16 downloads at once. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and ssh-many-connections 16 downloads at once; the row shows how long that took.
  • UDP. In the cases with a DNS query over UDP, the phone asked a public DNS server, over UDP through the tunnel, for the address the query came from. With UDP Relay on, the answer had to name the SSH server's address; with UDP Relay off, no answer could come.
  • The server's view. Each case read the server's sshd log, which shows how the user logged in or why the login failed.
  • Server settings. A row that names a server setting put that setting in a file of /etc/ssh/sshd_config.d/ for the case, reloaded sshd, and took it out afterwards. Rows that block a port did it with a firewall rule on the server, on its second SSH port 2222, so the test's own SSH session on port 22 kept working.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row.
  • Log levels. The cases named ssh-log-… moved 10 seconds of downloads, read the connection log back and checked its lines: Normal must show the connect line, the server's host key, the login and the session line, and no transfer counters, connection lines or packet engine lines; Expert adds the transfer counters; Debug adds a line for each connection and, on the iPhone, the packet engine's own lines (Android does not keep them); and no level may show the password. ssh-wrong-password also checked that the log names the reason the app closed the connection. On the iPhone the log cases, ssh-wrong-password and ssh-pass-download also ran on a Release build, the kind TestFlight ships; their rows show that run.
  • Lifecycle. The cases named ssh-life-… checked On Sleep; a session the server ended (the user's sshd processes stopped); a TCP connection the server reset (ss -K); a dead network path (every packet of the session dropped, without a reset, until the app gave the session up and tried a new connection); a switch to a new network path; port 2222 refusing connections until Retry Times ran out; and port 2222 refusing connections for 8 seconds. On Android the screen was really turned off and Wi-Fi was really switched off and on; on the iPhone the On Sleep case tells the tunnel that the phone slept, and the network case makes the tunnel open a new session as it does when Wi-Fi appears.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the downloads took most of the line.

Not tested in this round

  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel open a new session without a real change of network.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • SSH servers other than OpenSSH, such as Dropbear.
  • Logins with an SSH key. The app's SSH VPN profiles log in with a password.
  • IPv6 inside the tunnel. The app sends only IPv4 through it.
