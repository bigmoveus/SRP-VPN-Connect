How these tests ran

The phones were {iphone} and {android}, with {app}. The server was {server}, set up as ocserv (AnyConnect server) describes, with the profiles' Server Type AnyConnect unless a row says otherwise.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server on the internet. That server logged where each request came from, and every case that moves traffic checked that it came from the VPN server's address, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and the row shows how long that took.
  • The server's view. While a case ran, occtl show user read the phone's session on the server: its TLS version, and whether the VPN's packets went over DTLS (and which kind) or over TLS alone. Where a row shows how the ClientHello was sent, the server recorded the sizes of the phone's first TCP segments to port 443.
  • Server settings. A row that names a server setting changed that one setting in ocserv.conf for the case, restarted ocserv, and put the setting back afterwards. Our server ran with max-ban-score = 0 for every other case, so that the cases with wrong passwords would not block our address.
  • Path. The cases named ocv-path-… turned on ocserv's camouflage with a secret for the case and put ? and the secret, or a wrong one, in the profile's Path. They ran on a later commit than the other cases, the one that adds Path, on both phones.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row, or with the certificate warning declined.
  • Log levels. The cases named ocv-log-… read the connection log back and checked its lines: Normal must show the connect and session lines and none of OpenConnect's progress lines; Expert adds those and the routes; Debug adds the server's headers, with the server's cookies written as <elided>; and no level may show a TLS or DTLS secret. ocv-wrong-password also checked that the log names the reason the app closed the connection. On the iPhone these four cases ran on a Release build, the kind TestFlight ships, as well as on the Debug build.
  • Lifecycle. The cases named ocv-life-… checked On Sleep; a session the server ended (occtl disconnect user); a TCP connection the server reset while it kept the session (ss -K); a switch to a new network path; ocserv stopped until Retry Times ran out; and ocserv stopped for 8 seconds and started again. On Android the screen was really turned off and Wi-Fi was really switched off and on; on the iPhone the On Sleep case tells the tunnel that the phone slept, and the network case makes the tunnel move its session as it does when Wi-Fi appears.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the downloads took most of the line.

Not tested in this round

  • F5 BIG-IP and Palo Alto GlobalProtect servers. We had none; those Server Types were only tried against our AnyConnect server, which refuses them.
  • Cisco's own AnyConnect servers. Every AnyConnect case ran against ocserv.
  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel move its session without a real change of network.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel, and ranges the server keeps outside it (no-route).
