How these tests ran

The phones were {iphone} and {android}, with {app}. The server was {server}, set up as SoftEther VPN Server describes, with the users of each login method in the hubs DEFAULT and TEST-HUB.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server on the internet. That server logged where each request came from, and every case that moves traffic checked that it came from the VPN server's address, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and the row shows how long that took.
  • The server's view. Where a row names TCP connections, UDP acceleration or NAT-T, the server's SessionGet showed it for the phone's session while the case ran. In the cases that set Connections it was read about 10 seconds into the transfer; the app adds one connection per second, so with 32 the server counted fewer at that moment. Where a row shows how the ClientHello was sent, the server recorded the sizes of the phone's first TCP segments to port 443.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row, or with the certificate warning declined.
  • Log levels. The cases named sev-log-… read the connection log back and checked its lines: Normal must show the connect and session lines and neither the virtual adapter's DHCP line nor the core's own lines; Expert adds the DHCP line; Debug adds the core's lines; and no level may show a TLS session secret. sev-wrong-password also checked that the log names the reason the app closed the connection. On the iPhone these four cases ran on a Release build of commit 7708f7a3, the kind TestFlight ships, and again on a Debug build of the same commit, with the same result.
  • Proxies. The proxy cases went through HTTP CONNECT and SOCKS5 proxies and PAC files on a computer in our office network, with and without a username and password.
  • Lifecycle. The cases named sev-life-… checked On Sleep, a session the server disconnected (SessionDisconnect), the SoftEther service stopped until Retry Times ran out, and the service stopped for 8 seconds and started again. On Android the screen was really turned off; the iPhone's On Sleep case tells the tunnel that the phone slept.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the uploads took most of the line.

Not tested in this round

  • Moving between Wi-Fi and cellular. Every case ran on Wi-Fi; no test changed the network under a connected tunnel.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel. The hubs' SecureNAT hands out IPv4 addresses only.
  • NT Domain login. It needs SoftEther VPN Server on Windows; our server runs on Linux, and the RADIUS / NT Domain method was tested with RADIUS.
