Test Results

Every OpenVPN case we ran on 8 November 2026, with its result on an iPhone and on an Android phone: 76 of 76 cases passed on the iPhone and 65 of 65 on Android.

How these tests ran

The phones were an iPhone 12 with iOS 27.2 and a Samsung Galaxy A55 with Android 17, with the code of commit 48eaf2f7 on the iPhone, as a Debug build, and of cd3916be, which follows it, on Android, as a debug APK; the iPhone's rows of the ovpn-release-… cases come from a Release build of 48eaf2f7's code, the kind TestFlight ships. The server was OpenVPN 2.6.19 and stunnel 5.72 on Ubuntu 24.04, set up as OpenVPN server describes, with these additions for the tests: a management interface on each OpenVPN server, which the cases asked for the connected clients, a stunnel listener on port 9443 with a certificate of its own CA that also has the name cdn.example.com, one on port 9444 that allows only TLS 1.2, and three more OpenVPN servers that each differ from the UDP one in the setting their rows name.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server on the internet. That server logged where each request came from, and every case that moves traffic checked that it came from the OpenVPN server's address, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both, and ovpn-udp-many-connections ran 16 downloads at once. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and ovpn-udp-many-connections 16 downloads at once; the row shows how long that took.
  • UDP. In the case with a DNS query over UDP, the phone asked a public DNS server, over UDP through the tunnel, for the address the query came from; the answer had to name the OpenVPN server's address.
  • The server's view. While a case was connected, it asked the server's OpenVPN which clients it had, and from where: a phone that came through stunnel shows as 127.0.0.1. Each case also kept the server's log, which shows the cipher of the session, or why the server refused it.
  • TLS Fragmentation. The cases named ovpn-frag-… recorded on the server the first TCP segments the phone sent to stunnel, and checked their sizes.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row.
  • Log levels. The cases named ovpn-log-… moved 10 seconds of downloads (4 seconds at Debug), read the connection log back and checked its lines; no level may show the password or a key. The cases named ovpn-release-… ran on a Release build of the iPhone app, the kind TestFlight ships.
  • The guide's server. The cases named ovpn-guide-… ran last: the test setup was taken down, the server was set up again with the steps of OpenVPN server as the page shows them, and the phones used the page's own profiles for phone1 and vpnuser. That server has no management interface, so these cases read the server's log for the connection instead, and ovpn-guide-status-file its status file.
  • Lifecycle. The cases named ovpn-life-… checked On Sleep; a session the server restarted or halted (the management interface's client-kill); stunnel restarting; a dead network path (every packet of the session dropped, without a reset); a switch to a new network path; the server stopped until Retry Times ran out; and the server stopped for 8 seconds. On Android the screen was really turned off and Wi-Fi was really switched off and on; on the iPhone the On Sleep case tells the tunnel that the phone slept, and the network case makes the tunnel move its connection as it does when Wi-Fi appears.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the downloads took most of the line.

Not tested in this round

  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel move its connection without a real change of network.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel. Our server gives the phones IPv4 only.
  • Servers other than OpenVPN 2.6, such as OpenVPN Access Server or OpenVPN 3 servers, and tls-crypt-v2.
  • Importing a profile through the app's screens (From Files, From URL). The cases gave the app the profile's text as an import does; the import's checks were tested in the apps' unit tests.
