Configuration Reference

A WaterWall connection has two halves: the configuration file you write on the server, and the client file, the profile, that the app imports and runs. This page describes both, and what must match between them.

Where this page comes from

The server file below was read from our test server on 21 November 2026, where WaterWall 1.6.0 runs it. The app side was read from the app's source code at commit 367e594c. Which chains actually worked in our tests is on the Verified Test Scenarios pages; this page describes settings, not results.

Server configuration files

Each configuration is one JSON file in /etc/waterwall/configs/, listed in the configs array of /etc/waterwall/core.json (see Installation). WaterWall loads every listed file when it starts, so after adding or changing a file, restart the service:

systemctl restart waterwall.service
systemctl status waterwall.service --no-pager

What a file contains

A file has a name and a list of nodes. Each node has:

FieldMeaning
nameYour own name for the node, used by next.
typeThe kind of node, for example TcpListener or VlessServer.
settingsThe node's options.
nextThe name of the node that receives the traffic after this one. The last node has no next.

Our files also carry author, config-version and core-minimum-version.

Example: VLESS + TLS from our server

This is /etc/waterwall/configs/vless-tls.json from our server. Only the server name and the UUID are replaced with placeholders.

{
  "name": "vless-tls",
  "author": "SRP",
  "config-version": 1,
  "core-minimum-version": 0,
  "nodes": [
    {
      "name": "public-in",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 18443,
        "nodelay": true,
        "initial-idle-timeout-ms": 15000,
        "active-idle-timeout-ms": 300000
      },
      "next": "tls"
    },
    {
      "name": "tls",
      "type": "TlsServer",
      "settings": {
        "cert-file": "/etc/waterwall/fullchain.pem",
        "key-file": "/etc/waterwall/privkey.pem",
        "sni": "<SERVER_HOST>",
        "min-version": "TLSv1.2",
        "max-version": "TLSv1.3",
        "select-alpns": ["http/1.1"],
        "handshake-timeout-ms": 15000
      },
      "next": "vless"
    },
    {
      "name": "vless",
      "type": "VlessServer",
      "settings": {
        "uuid": "<UUID>",
        "connect": true,
        "udp": true,
        "verbose": true
      },
      "next": "outbound"
    },
    {
      "name": "outbound",
      "type": "TcpUdpConnector",
      "settings": {
        "address": "dest_context->address",
        "port": "dest_context->port",
        "nodelay": true
      }
    }
  ]
}
NodeWhat it does here
TcpListenerAccepts TCP connections on port 18443 from any address. Idle connections close after 15 seconds before any data, or 5 minutes after.
TlsServerEnds the TLS layer with the Let's Encrypt certificate. It accepts TLS 1.2 and 1.3 and offers the ALPN http/1.1, which is what the app sends for TLS.
VlessServerChecks the client's UUID and reads where each connection should go. connect and udp allow TCP and UDP destinations.
TcpUdpConnectorConnects to the real destination. dest_context->address and dest_context->port mean "the destination the client asked for".

The full list of options for every node is in the official WaterWall documentation.

Two values that are easy to miss
  • AEAD salt. WaterWall's own default salt for EncryptionServer is waterwall-encryption, but converted chains use waterwall-aead. Write the same salt on both sides, as our server does with "salt": "waterwall-aead".
  • HTTP path. Converted chains send the path /. If your HttpServer uses another path (one of our server files uses /tunnel), set the same path in the client's HttpClient settings.

The first server node depends on how the chain reaches the server:

  • TcpListener when the client chain ends in TcpConnector or TcpUdpConnector, including QUIC over TCP and RTMP.
  • UdpListener when it ends in UdpConnector: KCP, QUIC, ENet and GNS.

The server chain ends with a connector to the internet, normally TcpUdpConnector as above. For a Raw IPv4 chain, the server turns the stream back into packets with StreamToPackets and PacketsToConnection before the connector.

Packet Encryption on a Raw IPv4 chain

On a Raw IPv4 chain, an EncryptionClient in packet mode right after the HintPacketIN hint encrypts the TCP or UDP payload of each packet. This is the server side of our test chain, with no other layer; the address, certificate and password are examples. The client's password must be the same.

{
  "name": "rawip-packet",
  "nodes": [
    { "name": "public-in", "type": "TcpListener", "settings": { "address": "0.0.0.0", "port": 18480, "nodelay": true }, "next": "stream-in" },
    { "name": "stream-in", "type": "StreamToPackets", "settings": { "packet-validation-level": "hard" }, "next": "packet-crypto" },
    { "name": "packet-crypto", "type": "EncryptionServer", "settings": { "packet-mode": true, "algorithm": "xchacha20-poly1305", "password": "a-long-random-password", "salt": "waterwall-packet", "kdf-iterations": 12000 }, "next": "packet-out" },
    { "name": "packet-out", "type": "PacketsToConnection", "settings": { "mtu": 1420, "max-pending-bytes": 1048576 }, "next": "outbound" },
    { "name": "outbound", "type": "TcpUdpConnector", "settings": { "address": "dest_context->address", "port": "dest_context->port", "nodelay": true } }
  ]
}

The IP and TCP or UDP headers stay visible inside the chain and only TCP and UDP pass, so ping does not work through it.

The profile file

A profile is a WaterWall file like the server's, written for the client side, with one difference: instead of the nodes that take the phone's traffic, it starts with an input hint. You import it with Import JSON or build it node by node, and the app keeps it whole, secrets included, in the iOS Keychain or, on Android, encrypted with a key that the Android Keystore holds.

{
  "name": "VLESS over TLS",
  "nodes": [
    { "name": "input", "type": "HintConnectionIN", "settings": {}, "next": "vless" },
    { "name": "vless", "type": "VlessClient", "settings": { "uuid": "<UUID>", "address": "dest_context->address", "port": "dest_context->port", "protocol": "dest_context->protocol" }, "next": "tls" },
    { "name": "tls", "type": "TlsClient", "settings": { "sni": "<SERVER_HOST>", "verify": true }, "next": "uplink" },
    { "name": "uplink", "type": "TcpConnector", "settings": { "address": "<SERVER_HOST>", "port": 18443, "nodelay": true } }
  ]
}
RuleWhy
Exactly one hint, HintConnectionIN or HintPacketIN, with no settings, that no next namesThe app puts its input in the hint's place; the hint's type says whether the chain takes connections or IP packets.
No RawSocket, TunDevice, PacketsToConnection or NEPacketDevice anywhere in nodesThe app does not run raw sockets, and it supplies the input nodes itself.
Unique names; every next names a node; no cycleThe chain must be one path from the hint to the node without next.
A node that a setting names exists and is not the hint: the target of a Router rule, the upload and download of a HalfDuplexClient, the dns-next of a dns-behaviourWaterWall cannot start a chain that points to a node it does not have.

The messages for each broken rule are in Import JSON.

Nodes off the chain

The chain is the path from the hint along each next. A node reached another way, through one of the settings in the last rule above, is off the chain; it starts a branch of its own that also runs along next. The app keeps these nodes, lists them under OTHER NODES, and runs them with the profile.

This profile is WaterWall's striped RTMP and Reality example with the hint in place of its listener and SOCKS5 server. The chain ends at the HalfDuplexClient, which sends through the up branch, eight RTMP connections at a time, and receives through the down branch, one Reality connection.

{
  "name": "Striped RTMP upload, Reality download",
  "nodes": [
    { "name": "input", "type": "HintConnectionIN", "settings": {}, "next": "trojan" },
    { "name": "trojan", "type": "TrojanClient", "settings": { "password": "<TROJAN_PASSWORD>", "address": "dest_context->address", "port": "dest_context->port", "protocol": "dest_context->protocol" }, "next": "mux" },
    { "name": "mux", "type": "MuxClient", "settings": { "mode": "fixed-connections-count", "per-worker-connections-count": 1 }, "next": "half-duplex" },
    { "name": "half-duplex", "type": "HalfDuplexClient", "settings": { "upload": "up", "download": "down" } },

    { "name": "up", "type": "ConnectionStripeClient", "settings": { "connections": 8 }, "next": "obfuscator" },
    { "name": "obfuscator", "type": "ObfuscatorClient", "settings": { "method": "xor", "xor_key": 90 }, "next": "rtmp" },
    { "name": "rtmp", "type": "RtmpClient", "settings": { "tc-url": "rtmp://<SERVER_HOST>:1935/waterwall" }, "next": "rtmp-connector" },
    { "name": "rtmp-connector", "type": "TcpConnector", "settings": { "address": "<SERVER_HOST>", "port": 1935, "nodelay": true, "fastopen": false } },

    { "name": "down", "type": "RealityClient", "settings": { "sni": "<COVER_SITE>", "password": "<REALITY_PASSWORD>", "verify": true }, "next": "reality-connector" },
    { "name": "reality-connector", "type": "TcpConnector", "settings": { "address": "<SERVER_HOST>", "port": 443, "nodelay": true, "fastopen": false } }
  ]
}

The server side is the example's server file as WaterWall's page gives it, with the same passwords, cover site and ports. The upload path is plain RTMP with a reversible XOR, so use it only as that page describes.

Files in WaterWall's own syntax

Import JSON also reads what WaterWall's own loader reads beyond plain JSON:

  • Comments. Everything from // to the end of a line is skipped, except inside a string.
  • Variables. A top-level variables object holds values, and each unquoted $name$ in the file takes the value of that name. The app fills the values in when it imports and keeps the profile without the variables object, so change a value in the file before importing, or in the node afterwards. A name that variables does not define blocks the file.
  • The file's own local proxy. A client file written for a computer starts with a TcpListener or TcpUdpListener followed by a Socks5Server or HttpProxyServer. In a file without a hint, the app puts a HintConnectionIN named input in the place of that pair, because it supplies the input itself. A listener that leads anywhere else is not replaced, and the file is then blocked for having no hint.

What the app runs

Each time a profile connects, the app builds a separate copy for WaterWall and leaves the saved profile as it is:

  • The hint becomes the input chosen in Settings → WaterWall Input, linked to the hint's next:
    InputHintConnectionINHintPacketIN
    System VPN (TUN)packet device → PacketsToConnectionpacket device
    Local SOCKS5 proxyTcpUdpListener on 127.0.0.1:1080 → Socks5Serverrefused
    Local HTTP proxyTcpListener on 127.0.0.1:8080 → HttpProxyServerrefused
    The packet device is the app's own NEPacketDevice node, which reads and writes the VPN's packets in place of WaterWall's TunDevice. The added nodes are named srp-device, srp-connections, srp-socks5-listener, srp-socks5, srp-http-listener or srp-http-proxy, with -2, -3 and so on when the profile already uses that name.
  • Every connector with a fixed address is looked up once, its address is written into the copy, and the VPN's routes leave that address out, so the chain's own connections to the server do not loop through the VPN. This goes for the connectors of branches too. A name that cannot be looked up stops the connection with The WaterWall server address <name> could not be resolved. An address taken from the connection (dest_context->address, src_context->address), an IPv6 address and an address range such as 203.0.113.0/24 are left to WaterWall as they are.
  • A Router with geoip: or !geoip: rules, in destination-ip or source-ips, gets the path of the app's country database as its geoip-db-path; a path in the file is replaced. Without a valid database the connection stops with GeoIP is enabled but its database is unavailable: …
  • With Remote DNS (Fake IP) on, a HintConnectionIN chain and System VPN (TUN), PacketsToConnection answers DNS itself with placeholder addresses.
  • A HintPacketIN profile sends the phone's own packets, from the address 10.44.0.4. A server that checks the source address, such as a WireGuardServer peer's allowedips, must allow 10.44.0.4/32.

A Router rule with destination-domain needs the name of the site. With Remote DNS (Fake IP) on, each connection from the phone brings its name, and the rule matches it. With Remote DNS off, a connection brings only an address, and the rule matches only when the Router's own sniffing reads the name from the traffic: tls reads it from a TLS handshake and http1 from an HTTP request. The app's WaterWall also starts a Router with http2, http or quic in sniffing. We checked the name rule on 21 November 2026 with the app's WaterWall built for a Mac, through its local SOCKS5 input: with the name sent along, and by address with tls and with http1. The app has no GeoSite database: a rule with geosite: is refused.

A profile with another node type stops when it connects, with Node "<name>" is a <type> node, which the app's WaterWall does not include. Server nodes, and the nodes that need a raw socket or a device of the operating system (RawSocket, TunDevice, IpManipulator, FakeTcpHeaderClient, PingClient, Ping6Client), are not in the app. WaterWall checks each node's settings when it starts the chain, and a chain it refuses ends the connection with WaterWall refused the profile: … and its reason; the full list of options for every node is in the official WaterWall documentation.

These belong to WaterWall's core.json, which the app writes itself, so a profile cannot change them. Of a profile file the app passes on its name and its nodes; other top-level keys, such as author or config-version, are kept in the profile and not used.

The two pending-bytes values also limit TCP connections

Each TCP connection reserves max-pending-bytes of max-total-pending-bytes for as long as it lives, so the total divided by the per-connection value is how many can be open at once: 256 with these values. A new connection over that is refused, and iOS reports A TLS error caused the secure connection to fail. See Troubleshooting.

This limit is in the app only. The official server program has no such total: on a Raw IPv4 chain max-pending-bytes limits each TCP connection separately.

Chains of converted profiles

A profile saved by an earlier version of the app is converted once into the chain that version built from its settings (see the UI guide). Its nodes come in this order, each only when its setting was on:

Former settingChain after the hint
Chain, ConnectionsHintConnectionIN → DomainResolver (the former DNS resolver) → Router (Direct LAN Routing, GeoIP countries) → application → MUX → Obfuscator → HTTP → BGP4 framing → outer → KCP → connector
Chain, Raw IPv4HintPacketIN → Packet Encryption → PacketsToStream → Obfuscator → HTTP → BGP4 framing → outer → KCP → connector
DirectHintConnectionIN → TcpUdpConnector to each destination
WireGuardno chain: the profile becomes a WireGuard profile

QUIC with the former Stream carrier is QuicClient → UdpOverTcpClient → TcpConnector, which is how WaterWall 1.6.0 carries QUIC over TCP; the server needs UdpOverTcpServer between its TcpListener and QuicServer. A QUIC profile that build 47 or APK 1.2.0 (12) converted still has the carrier-mode setting of WaterWall 1.5, which 1.6.0 refuses: the app takes it out, and adds the UdpOverTcpClient node where it was stream, when it reads the profile.

The connector is UdpConnector for KCP and for QUIC over UDP, TcpUdpConnector for SOCKS5 and for VLESS, VMess or Trojan over TLS without MUX, an HTTP layer or a fixed protocol, and TcpConnector otherwise. The UUID or password, the SNI and certificate check, the TLS fragmentation sizes (a fragment object in the TlsClient or RealityClient), the router rules and the resolver servers are node settings of that chain.
