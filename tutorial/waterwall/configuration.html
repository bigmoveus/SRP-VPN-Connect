Configuration Reference

A WaterWall connection has two halves: the configuration file you write on the server, and the client chain the app builds from your choices. This page describes both, and what must match between them.

Where this page comes from

The server file below was read from our test server on 10 November 2026, after its move to WaterWall 1.5.42. The app side was read from the app's source code at commit e44cf11d, TestFlight build 41. The Android app builds the same chains; a test compares the two builders on the same configurations, see Android. Which combinations actually worked in our tests is on the Verified Test Scenarios pages; this page describes settings, not results.

Server configuration files

Each configuration is one JSON file in /etc/waterwall/configs/, listed in the configs array of /etc/waterwall/core.json (see Installation). WaterWall loads every listed file when it starts, so after adding or changing a file, restart the service:

systemctl restart waterwall.service
systemctl status waterwall.service --no-pager

What a file contains

A file has a name and a list of nodes. Each node has:

FieldMeaning
nameYour own name for the node, used by next.
typeThe kind of node, for example TcpListener or VlessServer.
settingsThe node's options.
nextThe name of the node that receives the traffic after this one. The last node has no next.

Our files also carry author, config-version and core-minimum-version.

Example: VLESS + TLS from our server

This is /etc/waterwall/configs/vless-tls.json from our server. Only the server name and the UUID are replaced with placeholders.

{
  "name": "vless-tls",
  "author": "SRP",
  "config-version": 1,
  "core-minimum-version": 0,
  "nodes": [
    {
      "name": "public-in",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 18443,
        "nodelay": true,
        "initial-idle-timeout-ms": 15000,
        "active-idle-timeout-ms": 300000
      },
      "next": "tls"
    },
    {
      "name": "tls",
      "type": "TlsServer",
      "settings": {
        "cert-file": "/etc/waterwall/fullchain.pem",
        "key-file": "/etc/waterwall/privkey.pem",
        "sni": "<SERVER_HOST>",
        "min-version": "TLSv1.2",
        "max-version": "TLSv1.3",
        "select-alpns": ["http/1.1"],
        "handshake-timeout-ms": 15000
      },
      "next": "vless"
    },
    {
      "name": "vless",
      "type": "VlessServer",
      "settings": {
        "uuid": "<UUID>",
        "connect": true,
        "udp": true,
        "verbose": true
      },
      "next": "outbound"
    },
    {
      "name": "outbound",
      "type": "TcpUdpConnector",
      "settings": {
        "address": "dest_context->address",
        "port": "dest_context->port",
        "nodelay": true
      }
    }
  ]
}
NodeWhat it does here
TcpListenerAccepts TCP connections on port 18443 from any address. Idle connections close after 15 seconds before any data, or 5 minutes after.
TlsServerEnds the TLS layer with the Let's Encrypt certificate. It accepts TLS 1.2 and 1.3 and offers the ALPN http/1.1, which is what the app sends for TLS.
VlessServerChecks the client's UUID and reads where each connection should go. connect and udp allow TCP and UDP destinations.
TcpUdpConnectorConnects to the real destination. dest_context->address and dest_context->port mean "the destination the client asked for".

The full list of options for every node is in the official WaterWall documentation.

Two values that are easy to miss
  • AEAD salt. WaterWall's own default salt for EncryptionServer is waterwall-encryption, but the app uses waterwall-aead. Write "salt": "waterwall-aead" in the server file, as our server does.
  • HTTP path. The app sends the path /. If your HttpServer uses another path (one of our server files uses /tunnel), set the same path in the app's HTTP advanced settings.

The first node depends on how the chain reaches the server:

  • TcpListener for the TCP carrier, including QUIC with the Stream carrier.
  • UdpListener for the KCP carrier and for QUIC with the Datagram carrier.

The server chain ends with a connector to the internet, normally TcpUdpConnector as above. For Raw IPv4, the server turns the stream back into packets with StreamToPackets and PacketsToConnection before the connector.

Packet Encryption on a Raw IPv4 chain

With Input Raw IPv4, the app's Packet Encryption switch encrypts the TCP or UDP payload of each packet. This is the server side of our test chain, with no other layer; the address, certificate and password are examples. It needs the same password in the app's Packet Password field.

{
  "name": "rawip-packet",
  "nodes": [
    { "name": "public-in", "type": "TcpListener", "settings": { "address": "0.0.0.0", "port": 18480, "nodelay": true }, "next": "stream-in" },
    { "name": "stream-in", "type": "StreamToPackets", "settings": { "packet-validation-level": "hard" }, "next": "packet-crypto" },
    { "name": "packet-crypto", "type": "EncryptionServer", "settings": { "packet-mode": true, "algorithm": "xchacha20-poly1305", "password": "a-long-random-password", "salt": "waterwall-packet", "kdf-iterations": 12000 }, "next": "packet-out" },
    { "name": "packet-out", "type": "PacketsToConnection", "settings": { "mtu": 1420, "max-pending-bytes": 1048576 }, "next": "outbound" },
    { "name": "outbound", "type": "TcpUdpConnector", "settings": { "address": "dest_context->address", "port": "dest_context->port", "nodelay": true } }
  ]
}

The IP and TCP or UDP headers stay visible inside the chain and only TCP and UDP pass, so ping does not work through it. The app does not offer it together with Reality or AEAD, which encrypt the whole stream and use the same password field in the app.

The client chain the app builds

You never write the client file; the app builds it each time you connect. Knowing its shape helps when you write the server side.

Mode and inputClient chain, in order
Chain, Connectionspacket device → PacketsToConnection → DomainResolver (only with the DNS resolver on) → Router → application → MUX → Obfuscator → HTTP → BGP4 framing → outer → KCP → connector
Chain, Raw IPv4packet device → Packet Encryption → PacketsToStream → Obfuscator → HTTP → BGP4 framing → outer → KCP → connector
Directpacket device → PacketsToConnection → TcpUdpConnector to each destination
WireGuardpacket device → WireGuardDevice → UdpStatelessSocket: WaterWall's own WireGuard, not the app's WireGuard protocol; see WireGuard mode.

Layers you did not choose are left out. The last node, the connector, is UdpConnector for KCP and QUIC Datagram, TcpUdpConnector for SOCKS5 and for VLESS, VMess or Trojan over TLS without MUX, an HTTP layer or a fixed protocol in the application's settings, and TcpConnector otherwise.

The DNS resolver

The DNS RESOLVER section of a Chain profile with Connections input puts WaterWall's DomainResolver node between PacketsToConnection and the router. It looks up the name of each connection on the phone before routing, so the router and GeoIP see real addresses and the server gets an address instead of a name. The names come from Remote DNS (Fake IP): with it off, the phone looks names up itself, connections arrive with addresses, and the node passes them on unchanged. The profile keeps it as domain-resolver, which becomes the node's settings unchanged.

ResolverNode settingsWhere the questions go
Off (default)no nodeThe server looks up the names the phone asks for. GeoIP still looks them up on the phone, as above.
Native{"mode": "native"}The DNS of the network the phone is on, outside the VPN.
Direct{"mode": "direct", "servers": [...]}The DNS servers you list, straight from the phone, outside the VPN.
Through the VPN{"mode": "chain", "servers": [...]}The DNS servers you list, through the VPN: the router's first rule, {"resolver-dns": true, "target": <application>}, sends the resolver's own questions to the application, even to a server in a GeoIP country or the local network. The server must allow UDP and reach those DNS servers.

Addresses sets strategy: prefer-ipv4, prefer-ipv6, only-ipv4, only-ipv6 or accept-dns-returned-order; the default, Default (IPv4 First), leaves it out, so WaterWall's own default applies. DNS Servers takes 1 to 32 addresses, separated by commas, spaces or new lines: an IPv4 or IPv6 address, or IPv4:port or [IPv6]:port; without a port, 53. A name, an IPv6 scope such as %en0, a leading zero or port 0 is refused. Through the VPN needs an application that carries UDP: not HTTP CONNECT, and not a fixed TCP protocol in the application's settings. Raw IPv4 input, Direct and WireGuard have no DNS resolver.

The two pending-bytes keys also limit TCP connections

Each TCP connection reserves max-pending-bytes of max-total-pending-bytes for as long as it lives, so the total divided by the per-connection value is how many can be open at once: 256 with the app's defaults. A new connection over that is refused, and iOS reports A TLS error caused the secure connection to fail. From the code only, not run: a max-pending-bytes above the total refuses every TCP connection, and the app's editor does not stop that. See Troubleshooting.

This limit is in the app only. The official server program has no such total: on a Raw IPv4 chain max-pending-bytes limits each TCP connection separately.

With Raw IPv4 input the Packet keys are instead packet-validation-level (none, loose or hard; the app uses hard), sensitive-mode, interval-ms and tolerance-ms. In Direct mode, Packet is the only layer.

The fragment object replaces the app's TLS Fragmentation option. It takes mode (counter with count, or timed with duration-ms), cuts (at most 64 entries of [offset, delay_ms, chance_percent] with increasing offsets), and optionally bypass_chance, wait-for-est, tls-hello-fragment and tls-hello-timeout-ms. When the app builds it from the TLS Fragmentation option, it uses counter mode, count 1, tls-hello-fragment on, a 1000 ms hello timeout, and a cut at the first-chunk size and then every following-chunk size, below 16384 bytes: 32 and 256 bytes for Auto, your First Chunk and Following Chunks for Manual.
