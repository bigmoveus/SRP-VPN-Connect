Troubleshooting

Start with the checks below, then look up the message you see.

Where this page comes from

The messages and what triggers them were read from the source code of the app at commit a03a8bc2 and of WaterWall, and on Android at commit 0fc837e3. The commands are the ones we use on our test server.

First checks

1. Open the app's log

Tap the status text under the power button. For more detail, set Log Level to Expert or Debug in the profile's OPTIONS and connect again.

2. Is WaterWall running on the server?

Run these on the server as root:

systemctl status waterwall.service --no-pager
ss -ltnup | grep -i waterwall
Check The service is active (running), and your configuration's port is in the list: TCP for TLS, Reality, AEAD, no outer layer, RTMP and QUIC over TCP; UDP for KCP, QUIC, ENet and GNS. The program shows as memfd:waterwall.

If the service does not start, its own messages say why:

journalctl -u waterwall.service -n 50 --no-pager
tail -n 50 /var/log/waterwall/core.$(date +%Y%m%d).log

After an upgrade from 1.5.3, a configuration file with a name that 1.5.4 and later refuse stops the whole program at start, with one of these lines (we started WaterWall 1.6.0 with two of our server's 1.5.3 files to see them):

MessageWhat happenedWhat to change
FATAL JSON Error: TcpUdpConnector->settings no longer accepts domain-strategy or resolve-domains; use dns-behaviourA node's settings still have domain-strategy or resolve-domains. The line names the node type.Remove the setting, or use dns-behaviour; see Upgrading from 1.5.3.
FATAL NodeManager: node creation failure: library "TcpOverUdpServer" (hash: …) could not be loadedThe KCP node has a new name since 1.5.4."type": "KcpServer" on the server (KcpClient on a client).

3. Is the port open in the firewall?

ufw status numbered

The port and its protocol (tcp or udp) must be allowed. A KCP, QUIC, ENet or GNS chain needs a UDP rule; a TCP rule for the same number does not help.

4. Do the two halves match?

Compare the profile's chain with the server file, node by node, using The server node for each client node. The most common mistakes are a different port, a different UUID or password, a missing or extra node (for example MUX on one side only), and an HTTP path that differs between HttpClient and HttpServer.

5. Can the server reach the internet?

When it connects, the app checks the tunnel by opening a test connection to 1.1.1.1 on TCP port 80, and for chains that carry UDP, a DNS query to 1.1.1.1; with a local proxy as the input, it asks for http://1.1.1.1/ through the proxy. These go through your server, so the server must be allowed to reach 1.1.1.1 on those ports.

curl -sS -o /dev/null -w "%{http_code}\n" http://1.1.1.1/

Any HTTP status code means the server can reach it. On our server it prints 301. An error such as Connection timed out means something blocks the server's outgoing traffic.

Messages and what they mean

When saving a profile

An alert titled Invalid WaterWall Configuration names the node or the next to fix. Import JSON refuses a file for the same reasons, in a red Import blocked banner; the full list is in the UI guide.

In the logs

These lines explain why one request can fail, for example with A TLS error caused the secure connection to fail or The network connection was lost, while the connection stays up.

MessageWhat happenedWhat to check
DomainResolver: async dns resolve failed for <name>: Timeout while contacting DNS servers, in /var/log/waterwall/dns.YYYYMMDD.log on the serverThe server could not get a DNS answer for that name in time and closed that connection.The server's DNS. WaterWall 1.6.0 tries 5 times by default; if core.json sets "dns": {"tries": …}, keep it at 5 or more.
QuicServer: closing association: application backlog budget exceeded, in /var/log/waterwall/network.YYYYMMDD.log on the serverThe server's queue for one QUIC connection passed its max-buffered-bytes, so the server closed that connection, and the requests on it failed.max-buffered-bytes on both ends; see the Configuration Reference. The app opens a new QUIC connection for the next request.
QuicServer: closing association: Network blackhole detected, in the same logThe server got no acknowledgement on one QUIC connection for several retransmission timeouts in a row and closed it, for example during a network outage.The network at that time. The app opens a new QUIC connection for the next request.
TcpListener: closing connection: write retention admission refused, in the same logThe client took the data of one connection more slowly than it arrived, the server's queue for that connection reached its fixed limit of 16 MiB, and the server closed the connection. On a chain that carries many requests in one connection, such as the download connection of a HalfDuplexServer pair under a MUX, every request open at that moment failed. We saw it on our server, which has two workers, with the RTMP and Reality profile and four downloads and four uploads at once: in 3 of 16 runs of 60 seconds. A copy of that chain, run on the same server by the same program with "workers": 1 in its core.json, did not show it in 10 runs, at the same speed.The app opens new connections by itself, so only the requests of that moment are lost. If the line appears often, run that server with one worker.
PacketsToConnection: TCP aggregate pending-byte budget is full; refusing a new flow, in WaterWall's log inside the app, which on iOS the app keeps only in test runs; on Android it is in the app's log at Expert or Debug.More TCP connections were open than the packet budget allows, so the new one was refused. iOS shows it as the TLS error.max-total-pending-bytes divided by max-pending-bytes is the limit. The app's defaults allow 256. Keep the defaults, or do the division first; see the Configuration Reference.

Certificates

With "verify": true in the chain's TlsClient, the connection refuses a server certificate that is not valid for the client's sni. If your server has a Let's Encrypt certificate for its domain, use that domain as the sni. Turning verification off hides the problem but lets someone between you and the server pretend to be it, so fix the certificate instead.
