Troubleshooting

Start with the checks below, then look up the message you see. The last section lists the problems that showed up in our own tests.

Where this page comes from

The messages and what triggers them were read from the app's source code at commit dfce868f. The commands are the ones we use on our test server. The problems in the last section come from our test runs of 1 November 2026.

First checks

1. Open the app's log

Tap the status text under the power button. For more detail, set Log Level to Expert or Debug in the profile's OPTIONS and connect again.

2. Is WaterWall running on the server?

Run these on the server as root:

systemctl status waterwall.service --no-pager
ss -ltnup | grep -i waterwall
Check The service is active (running), and your configuration's port is in the list: TCP for TLS, Reality, AEAD, no outer layer and QUIC Stream, UDP for KCP and QUIC Datagram. The program shows as memfd:waterwall, because WaterWall restarts itself from memory when it starts.

If the service does not start, its own messages say why:

journalctl -u waterwall.service -n 50 --no-pager
tail -n 50 /var/log/waterwall/core.$(date +%Y%m%d).log

3. Is the port open in the firewall?

ufw status numbered

The port and its protocol (tcp or udp) must be allowed. A KCP or QUIC Datagram chain needs a UDP rule; a TCP rule for the same number does not help.

4. Do the two halves match?

Compare the app's choices with the server file, layer by layer, using The server node for each app choice. The most common mistakes are a different port, a different UUID or password, a missing or extra layer (for example MUX on one side only), and an HTTP path that differs from /.

5. Can the server reach the internet?

When it connects, the app checks the tunnel by opening a test connection to 1.1.1.1 on TCP port 80, and for chains that carry UDP, a DNS query to 1.1.1.1. These go through your server, so the server must be allowed to reach 1.1.1.1 on those ports.

curl -sS -o /dev/null -w "%{http_code}\n" http://1.1.1.1/

Any HTTP status code means the server can reach it. On our server it prints 301. An error such as Connection timed out means something blocks the server's outgoing traffic.

Certificates

With TLS Server Verification on, the app refuses a server certificate that is not valid for the name it sends: the SNI, or the Server field when SNI is empty. If your server has a Let's Encrypt certificate for its domain, type that domain in Server and leave SNI empty. Turning verification off hides the problem but lets someone between you and the server pretend to be it, so fix the certificate instead.

Problems seen in our tests

These come from our test runs of 1 November 2026, with the official WaterWall 1.5.2 program on the server. Each result is on its scenario page.

Downloads stop before the end with KCP, QUIC, MUX or HTTP/2

With these layers in the chain, downloads through the tunnel stopped before they finished, while uploads in the same test kept working and the app stayed connected. In Safari this looks like a page or a file that stops loading. With Input set to Connections:

Layer in the chainProduction serverCombinations
KCP0 of 3 passed0 of 7 passed without MUX; the 2 with MUX and HTTP or WebSocket passed
QUIC Datagram or QUIC Stream, without MUX0 of 4 passed0 of 9 passed
MUX1 of 9 passed5 of 17 passed
HTTP/2, without MUX0 of 2 passed0 of 3 passed

With Input set to Raw IPv4, the same layers passed: Raw IPv4 + KCP and Raw IPv4 + QUIC Datagram on the production server, and all 4 Raw IPv4 combinations with KCP or QUIC. HTTP/1.1 and WebSocket passed in all 11 combinations without MUX.

Why, for KCP: when the destination closes its connection right after its last data, as the test server does after each download, WaterWall's KCP server (TcpOverUdpServer) sends what fits in one round and then discards the rest of that connection's queued data. The phone keeps waiting for the rest until the request times out. We found this in WaterWall 1.5.2 and in WaterWall's current source, and reproduced it without the app. With Raw IPv4 the phone's own TCP connections run inside one long KCP connection, so nothing is cut off. For QUIC, MUX and HTTP/2 we have not found the cause.

What to do: until a WaterWall release fixes this, use a chain without these layers, such as VLESS + TLS or VLESS + Reality, which passed in every run, or set Input to Raw IPv4 if you need KCP or QUIC.

A UDP exchange that is open while WaterWall restarts

If WaterWall stops inside the app, the app starts it again after 2 seconds; the log then shows reconnecting in 2s. In our runtime recovery test, downloads and a new UDP exchange worked after the restart. In one run of the same test, the UDP exchange had started just before the restart, and it got no more answers after it. That exchange used an address that WaterWall's built-in DNS had given out before the restart, and the restarted WaterWall starts with an empty list of those addresses. Downloads recovered because each request opened a new connection. If an app that uses UDP, such as a call or a game, stops working after this message, make it connect again, for example by closing and reopening it.

Very small packet budgets

In our test with max-pending-bytes 8192 and max-total-pending-bytes 65536 on PacketsToConnection, set in the advanced node settings, 2 of the test's connections were reset during their TLS handshake right at the start. iOS reports this as A TLS error caused the secure connection to fail. The other transfers completed. We have not confirmed which limit reset them; keep the defaults unless you need to limit memory.
