Verified Test Scenarios

Every WaterWall combination we tested on 9 and 10 November 2026, with the app against the official WaterWall 1.5.42 release on our server. Each page shows the server file, the app settings, how the test ran and what happened.

How these tests ran

All tests used our iPhone 12 with iOS 27.2 and the official WaterWall 1.5.42 program, unchanged, on our Ubuntu test server, in five kinds of test.

  • Production server. The app connected to every configuration our permanent waterwall.service loads, with its Let's Encrypt certificate and TLS Server Verification on: the setup the guides describe.
  • Combinations. For each case, a test harness started a separate copy of the same program on the server with the matching server chain on port 4097, and the app connected to it. These copies used a self-signed certificate, so TLS Server Verification was off.
  • UDP and GeoIP routing. Chains that carry UDP were checked with a UDP echo server, and the GeoIP cases were checked for which way their downloads went.
  • DNS resolver. Chains with the DNS resolver on were checked for where its questions went, with a DNS test server on the server that logs where each question comes from.
  • Connection lifecycle. Checks of reconnecting, Retry Times, On Sleep and Auto Switch on the VLESS + TLS chain.

The production server's chains ran on app commit e44cf11d, which is TestFlight build 41 and contains WaterWall 1.5.42, and its four KCP chains on f4425e02; the other tests ran on e69cb668. The commits after e44cf11d change only the tests and the change log, so every test ran build 41's app. On Raw IPv4 and native WireGuard chains iOS keeps the server's own address out of the tunnel, so their traffic went to a private address of the server. For every case except Direct mode and the GeoIP cases, which leave outside the tunnel by design, the test checked that the traffic arrived through the tunnel.

Every scenario page describes its procedure in full. A page whose case ran more than once says how many runs passed.

The server files and app settings on these pages apply to Android too. The Android results are on the Android page.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYEvery check passed, in every run.
TESTED — PARTIALLY WORKINGTraffic moved, but not every check passed in every run; the page says what failed.
TESTED — FAILEDThe first run moved no traffic; the page says what happened and whether a later run passed.

Speeds are averages over the whole test on our office line. They show that traffic moved, and are not a benchmark.

Not tested in this round

  • Real sleep and network changes. The sleep checks tell the tunnel the phone slept; the phone did not really sleep, and no test moved between Wi-Fi and cellular. Both need a person at the phone.
  • Auto Switch on packet loss. Only the switch after a failed connection was tested; the loss rule needs a lossy network.
  • Most combinations. The app accepts far more combinations than were run. The selection covers every outer layer, application and carrier, every chain our production server runs, BGP4 framing, and a set of advanced settings.
