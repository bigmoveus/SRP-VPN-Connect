Test Results

Every SSTP case we ran on 6 November 2026, with its result on an iPhone and on an Android phone: 227 of 227 cases passed on the iPhone and 230 of 230 on Android.

How these tests ran

The phones were our iPhone 12 with iOS 27.2 and a Samsung Galaxy A55 with Android 17, with the iPhone running a Release build of commit 778e1b69, whose SSTP code TestFlight build 34 has, and Android running debug builds of this round's Android app, the one for Windows Server 2025 at commit 3bcb0567. The servers were MikroTik RouterOS 7.25, SoftEther VPN Server 4.44, and Windows Server 2019, 2022 and 2025 with Routing and Remote Access, the last with FreeRADIUS 3.2.5, set up as the guides in this section describe.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server on the internet. That server logged where each request came from, and every case that moves traffic checked that it came from the VPN server's address, so it went through the tunnel.
  • Traffic. On the iPhone a download, an upload, or both at once ran for the time shown. On Android, which ran beside the iPhone, each traffic case moved 4 MiB down and 4 MiB up instead.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row.
  • Proxies. The proxy cases went through a test proxy on our office network, with and without a username and password, set by hand or by a PAC file.
  • Log levels. The cases named sstp-log-… and sstp-wrong-password read the connection log back and checked its lines: Normal must show the connect line and the PPP link and neither the PPP phases nor the SSTP client's own lines; Expert adds the phases; Debug adds the client's lines; the refused login's log names the reason; and no level may show a TLS session secret.
  • Lifecycle. The cases named mt-life-… and android-life-… checked On Sleep, a session the server dropped, and Retry Times running out while the server was off.

The iPhone rows of sstp-papchap-only, sstp-no-auth-method, mt-srv-mschap1-only, mt-srv-pap-client-mschapv2-only, se-verify-declined, se-eap-mschapv2, win2019-peap-identity-privacy, win2025-ttls-mschapv2, win2025-ttls-eap and se-securenat-download come from a Release build of commit 3bcb0567, whose SSTP code TestFlight build 35 has, and that of mt-life-retry-exhausted from a Debug build of it. On 7 November the iPhone ran the log cases sstp-log-normal, sstp-log-expert and sstp-log-debug and the case sstp-wrong-password on a Release build of commit a098b9e5, the kind TestFlight ships, and their iPhone rows show that run; a Debug build of the same commit gave the same result. Android ran sstp-log-normal with a debug build of commit 013f04fb.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark.

Not tested in this round

  • Moving between Wi-Fi and cellular. Every case ran on Wi-Fi; no test changed the network under a connected tunnel.
  • Real sleep on the iPhone. The iPhone's On Sleep cases tell the tunnel that the phone slept; the phone did not really sleep. On Android the screen was really turned off.
  • IPv6 inside the tunnel. The app asks the servers for IPv4 only.
  • Certificate login against Windows' own Network Policy Server. It needs an Active Directory domain, which our servers are not part of; certificate login (EAP-TLS) was tested through FreeRADIUS on Windows Server 2025.
