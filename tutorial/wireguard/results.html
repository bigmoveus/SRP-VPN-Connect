Test Results

Every WireGuard case we ran on 8 November 2026, with its result on an iPhone and on an Android phone: 40 of 40 cases passed on the iPhone and 35 of 35 on Android.

How these tests ran

The phones were an iPhone 12 with iOS 27.2 and a Samsung Galaxy A55 with Android 17, with the code of commit 3731b356 on the iPhone, as a Debug build, and of c1410582, which follows it, on Android, as a debug APK; the iPhone's rows of the wg-release-… cases come from a Release build of 3731b356's code, the kind TestFlight ships. The server was WireGuard in the Linux kernel 6.8 on Ubuntu 24.04, with wireguard-tools 1.0.20210914: a wg0 like the one WireGuard server sets up, on port 51821, with a peer of its own for each phone and for the files without a preshared key and with the wrong one.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server that runs on the WireGuard server itself. That test server logged where each request came from, and every case that moves traffic checked that it came from the phone's own address in the tunnel, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both, and wg-many-connections ran 16 downloads at once. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and wg-many-connections 16 downloads at once; the row shows how long that took.
  • UDP. In the cases with a DNS query over UDP, the phone asked a public DNS server for the address the query came from: through the tunnel the answer has to name the server's address, and in the split tunnel the phone's own network.
  • The server's view. While a case was connected, it asked the server's WireGuard (wg show) when its peer last had a handshake.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row.
  • Log levels. The cases named wg-log-… moved 40 seconds of downloads (4 seconds at Debug), read the connection log back and checked its lines; no level may show a key. The cases named wg-release-… ran on a Release build of the iPhone app, the kind TestFlight ships.
  • Lifecycle. The cases named wg-life-… checked On Sleep; the server's WireGuard restarting (wg-quick), stopped for 8 seconds, stopped for 150 seconds without Auto Reconnect and for 120 seconds with Retry Times 2; a dead path (every packet of the session dropped, without a reset); and a change of network. On Android the screen was really turned off and Wi-Fi was really switched off and on, with pings through the tunnel to the server's tunnel address answered over mobile data in between (for that case the server's firewall also accepted the phone's mobile address), and a ping from the phone's shell kept traffic going while the server was away; on the iPhone the On Sleep case tells the tunnel that the phone slept, and the network case makes the tunnel move its sockets as it does when the network changes.
  • The guide's server. The cases named wg-guide-… ran last: the test setup was taken down, the server was set up again with the steps of WireGuard server as the page shows them, and the phones used the page's own files for phone1 and the removed phone2.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the downloads took most of the line.

Not tested in this round

  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel move its sockets without a real change of network.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel, and an IPv6 endpoint. Our server has no IPv6 address.
  • Servers other than the kernel's WireGuard, such as a router's or a commercial service's.
  • Importing a file through the app's screens on the iPhone. The cases gave the app the file's text as an import does; the import's checks were tested in the apps' unit tests, and on Android a Release build imported a file through the system's file picker.
