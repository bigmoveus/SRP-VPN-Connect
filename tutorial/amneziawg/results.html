Test Results

Every AmneziaWG case we ran on 9 November 2026, with its result on an iPhone and on an Android phone: 70 of 70 cases passed on the iPhone and 65 of 65 on Android.

How these tests ran

The phones were an iPhone 12 with iOS 27.2 and a Samsung Galaxy A55 with Android 17, with the code of commit 0a699819 on both phones, as a Debug build on the iPhone and as a debug APK on Android; the iPhone's awg-release-… rows come from a Release build of the same code, the kind TestFlight ships, and the awg-kernel-module-… rows on both phones from builds with the same engine made before 0a699819's change to the log note. The server was our amneziawg-go fork (github.com/bigmoveus/amneziawg-go, tag v3.1.20260828-srp.1, built as AmneziaWG server shows) with amneziawg-tools 3.1.20260812 from the Amnezia packages, on Ubuntu 24.04 with Linux 6.8: eight interfaces like the one AmneziaWG server sets up, awg0 to awg7 on UDP ports 51830 to 51837, one for each generation of AmneziaWG (the Settings column names it; awg7 is awg4 without a header protection key), with a peer of its own for each phone and for the files without a preshared key and with the wrong one.

  • Each case saved a profile with the settings in its row, connected, and moved the traffic in its row through the tunnel to a test server that runs on the AmneziaWG server itself. That test server logged where each request came from, and every case that moves traffic checked that it came from the phone's own address in the tunnel, so it went through the tunnel.
  • Traffic. On the iPhone four 16 MiB transfers at a time ran for the time shown, as downloads, uploads or both, and awg-many-connections ran 16 downloads at once. On Android each transfer case moved two 16 MiB downloads, two 16 MiB uploads, or both, and awg-many-connections 16 downloads at once; the row shows how long that took.
  • UDP. In the cases with a DNS query over UDP, the phone asked a public DNS server for the address the query came from: through the tunnel the answer has to name the server's address, and in the split tunnel the phone's own network.
  • The server's view. While a case was connected, it asked the server (awg show) when its peer last had a handshake.
  • Refusals. A case whose expected result is refused passed when the app did not connect and ended with the message shown in its row. The cases named awg-life-s4-… and awg-life-h4-… connect, as the server answers their handshake, and pass when the app then ends the VPN with the message for traffic that is not answered.
  • Log levels. The cases named awg-log-… moved 40 seconds of downloads (4 seconds at Debug) on the AmneziaWG 3.0 interface, read the connection log back and checked its lines; no level may show a key, nor the values of the file's private key, preshared key and header protection key. The cases named awg-release-… ran on a Release build of the iPhone app, the kind TestFlight ships.
  • Idle sessions. The cases named awg-idle-… held a session without traffic for 3 minutes, with padding (3.0) and with random trailers (3.1): the log must show no server counted as gone and no new handshake, and a transfer must pass before and after.
  • Lifecycle. The cases named awg-life-… checked On Sleep; the server's interface restarting (awg-quick), stopped for 8 seconds, stopped for 150 seconds without Auto Reconnect and for 120 seconds with Retry Times 2; a dead path (every packet of the session dropped, without a reset); and a change of network. On Android the screen was really turned off and Wi-Fi was really switched off and on, with pings through the tunnel to the server's tunnel address answered over mobile data in between, and a ping from the phone's shell kept traffic going while the server was away; on the iPhone the On Sleep case tells the tunnel that the phone slept, and the network case makes the tunnel move its sockets as it does when the network changes.
  • The kernel module. The cases named awg-kernel-module-… ran before the server moved to our fork, against AmneziaWG's kernel module from the Amnezia packages (amneziawg-dkms built from the module's tag of 6 September 2026), unchanged: a server as AmneziaWG's own releases set it up, with the same phones and the same code.
  • The guide's server. The cases named awg-guide-… ran last: the test setup was taken down, the server was set up again with the steps of AmneziaWG server as the page shows them, and the phones used the page's own files for phone1 and the removed phone2.

How to read the results

LabelMeaning
VERIFIED — TESTED SUCCESSFULLYThe case did what its row expects: it connected and moved its traffic through the tunnel, or it was refused with the message shown.
TESTED — FAILEDThe case did not do what its row expects; the row says what happened.
NOT VERIFIEDThe case did not run on that phone.

Speeds are averages over the whole transfer on our office line. They show that traffic moved, and are not a benchmark. When both directions ran at once on the iPhone, the uploads took most of the line.

Not tested in this round

  • Moving between Wi-Fi and cellular on the iPhone. The iPhone's network case makes the tunnel move its sockets without a real change of network.
  • Real sleep on the iPhone. The iPhone's On Sleep case tells the tunnel that the phone slept; the phone did not really sleep.
  • IPv6 inside the tunnel, and an IPv6 endpoint. Our server has no IPv6 address.
  • Other servers: the Amnezia app's own servers, Amnezia Premium, and AmneziaWG's kernel module beyond the awg-kernel-module-… cases. amneziawg-go as Amnezia releases it, without our fix, only in the lab, with pings.
  • A real censoring network. The cases show that each setting connects and moves traffic; whether a given network's filters recognize the traffic was not tested.
  • Importing a file through the app's screens on the iPhone. The cases gave the app the file's text as an import does; the import's checks were tested in the apps' unit tests, and on Android a Release build imported a file through the system's file picker.
